## 1. Стек

| Компонент | Рішення |
|---|---|
| Платформа | .NET 10 LTS, C# 14, `net10.0`; версія SDK зафіксована в `global.json` |

| Міграції | окремі проєкти для SQLite і PostgreSQL - щоб набори не перебивали один одного |
| API | ASP.NET Core, DTO окремим проєктом, OpenAPI |
| Клієнт | .NET MAUI (Android і Windows), локальна база, черга синхронізації |

| Розгортання | Docker і docker compose |

## 2. Структура репозиторію

```
src/Lab.Domain             сутності й правила предметної області (без EF і без залежностей)
src/Lab.Contracts          DTO і моделі запитів, які бачить клієнт
src/Lab.Application        сервіси, абстракції, розрахункове ядро
src/Lab.Infrastructure     LabDbContext, Fluent-конфігурації, вибір провайдера
src/Lab.Migrations.Sqlite  міграції для SQLite і фабрика часу проєктування
src/Lab.Migrations.Postgres міграції для PostgreSQL і фабрика часу проєктування
src/Lab.Api                контролери, безпека, обробка помилок, OpenAPI
src/Lab.Worker             фоновий обробник
src/Lab.Client.Maui        клієнт (створює власник зони Z4)
tests/                     тести домену, сервісів і PostgreSQL
docs/                      ТЗ, архітектура, лог рішень, приймальні кейси, декларація
docker/                    локальна PostgreSQL
scripts/                   службові скрипти
```

Напрямок залежностей - тільки всередину: `Api` → `Application` → `Domain`;
`Infrastructure` реалізує абстракції прикладного шару. Домен не знає ні про EF Core,
ні про ASP.NET, ні про MAUI. Це перевіряється тестом архітектури.

## 3. Збірка, тести, покриття

```bash
dotnet build LabStem.Server.slnf -c Release          # попередження вважаються помилками
dotnet test LabStem.Server.slnf                      # тести PostgreSQL позначаться пропущеними

docker compose -f docker/dev-postgres.yml up -d
LAB_TEST_POSTGRES=1 dotnet test LabStem.Server.slnf  # усі тести, включно з PostgreSQL

dotnet test LabStem.Server.slnf -c Release --collect:"XPlat Code Coverage" --results-directory TestResults
python3 scripts/coverage-summary.py           # зведення покриття і перевірка порога
```

Порогове значення - **80 % покриття ядра** (домен, прикладний шар, інфраструктура). Скрипт
повертає помилку, якщо поріг не витримано, тому й CI стає червоним.

## 4. Правила коду

- **Сирий SQL для запису заборонений** - тільки EF Core і LINQ. Читання сирим SQL - тільки з
  параметрами й окремим обґрунтуванням.
- **Секрети не потрапляють у репозиторій**: паролі, ключі й рядки підключення з паролями живуть
  у змінних середовища; у файлах - `.env.example` із заглушками.
- **Ніяких `TODO` і заглушок у merge.** Незавершена робота лишається в гілці.
- `async/await` до кінця: без `.Result` і `.Wait()`.
- `Nullable` увімкнений: `string?` - це сигнал, що значення може не бути; попередження `!` не
  «глушимо».
- **Попередження аналізатора - це помилка.** Послаблення робимо точково у проєкті, де код
  згенерований (міграції), а не для всього solution.
- Один клас - одна відповідальність: контролер не торкається бази, сервіс не знає про
  `HttpContext`, домен не знає про базу.

## 5. Правила даних

- **Третя нормальна форма.** Денормалізація - тільки з поясненням у `docs/decisions-log.md`.
- **PK/FK на кожному зв'язку** і свідомо обрана політика видалення (`Cascade`, `Restrict`,
  `SetNull`) із поясненням у конфігурації.
- **Індекси під реальні запити**: поля фільтрації, сортування й JOIN; унікальні індекси для
  природних ключів (`SerialNumber`, `ClientId`).
- **Транзакції** там, де змінюється більше однієї сутності.
- **Схему створюють міграції**, а не `EnsureCreated`. Одна зміна моделі - два набори міграцій
  (SQLite і PostgreSQL) і два `database update`.
- Дати зберігаємо в UTC; з `DateTimeOffset` на SQLite обережно - він не сортує такі значення.

## 6. Правила API

- **Контракт спершу**: новий ендпойнт починається з DTO і моделі запиту, а не з контролера.
- Коди відповідей: `200/201/204` успіх, `400` валідація, `401` не автентифікований, `403` без
  прав, `404` ресурсу немає, `409` конфлікт.
- Помилки - у форматі `ProblemDetails` через єдиний обробник; трасування стеку назовні немає.
- Пагінація обов'язкова для колекцій, `pageSize` обмежений зверху.
- OpenAPI оновлюється в тому ж PR, у якому змінився ендпойнт.
- Розрахункові ендпойнти повертають числа разом із похибкою та одиницями виміру.

## 7. Правила безпеки

- JWT з підписом HS256; ключ тільки зі змінної середовища, час життя обмежений, `ClockSkew = 0`.
- Ролі: `Researcher` (свої серії), `LabManager` (серії свого майданчика й підпис),
  `Administrator` (користувачі й прилади).
- **Володіння ресурсом** перевіряється в сервісному шарі, а не «десь вище»: чужий ресурс не
  редагується.
- Пароль зберігається тільки як хеш із сіллю; відповідь на невдалий вхід однакова для
  «немає користувача» і «невірний пароль».
- Підпис серії, зміна ролі й видалення серії пишуться в журнал аудиту.

## 8. Клієнт і синхронізація

- Локальна база - SQLite з тією ж моделлю й тими самими конфігураціями сутностей.
- Кожен вимір отримує `ClientId` (UUID) на пристрої - це ключ ідемпотентності синхронізації.
- Черга операцій має стани `Pending / Sent / Failed`; повторна відправка не створює дубль.
- Конфлікти вирішуються за версією запису; політика описана й покрита тестами.
- Офлайн-режим обов'язковий: застосунок працює без мережі й показує стан синхронізації.

## 9. Гілки, коміти, рев'ю

1. Задача починається з issue з критеріями приймання.
2. Гілка від `main`: `feature/<номер>-<коротка-назва>`, `fix/...`, `docs/...`, `test/...`.
3. Код і тести - в одному PR. **Прямі коміти в `main` заборонені** (гілка захищена).
4. PR описується за шаблоном із розділу 11; потрібне схвалення іншого учасника.
5. Merge - тільки після зеленого CI.
6. Гілка видаляється після merge; force-push у `main` заборонений.

**Коміти:** `<тип>(<область>): <що зроблено>`, типи `feat`, `fix`, `test`, `docs`, `refactor`,
`chore`, `perf`. Приклад: `feat(measurements): відхиляти значення поза діапазоном приладу`.
Повідомлення українською, один коміт - одна думка.

## 11. Визначення готовності

Задача готова, коли виконано все:

- [ ] збірка без попереджень (`dotnet build -c Release`: 0 Warning, 0 Error);
- [ ] тести на нову поведінку, включно з крайніми випадками;
- [ ] покриття ядра не знизилось і тримається ≥ 80 %;
- [ ] `dotnet test` зелений локально і в CI;
- [ ] зміна схеми БД → міграції в обох наборах і застосовані на обох СУБД;
- [ ] оновлено OpenAPI (якщо змінився API) і `docs/decisions-log.md` (якщо було рішення);
- [ ] PR містить вивід перевірки та чесний опис ризиків;
- [ ] за потреби оновлено `docs/acceptance-cases.md`.

## 13. Використання інструментів генерації коду

Кафедра дозволяє використовувати інструменти генерації коду за обов'язкової умови декларування.
Декларація ведеться у файлі [docs/META-USAGE.md](docs/META-USAGE.md): кожен учасник зазначає,
які інструменти застосовував, для яких задач і як перевіряв результат.

Згенерований код приймається на тих самих умовах, що й написаний вручну: він мусить збиратися
без попереджень, мати тести й бути зрозумілим автору зони. Якщо учасник не може пояснити
фрагмент - він не потрапляє в `main`.
