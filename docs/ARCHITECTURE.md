# Архітектура

Документ фіксує рішення, які не змінюються на ходу. Зміна будь-якого пункту - через issue і PR.

## 1. Шари й напрямок залежностей

```
Lab.Api  ─┐
          ├─→ Lab.Application ─→ Lab.Domain
Lab.Worker┘        ↑                    ↑
                   │                    │
        Lab.Infrastructure ─────────────┘
                   ↑
        Lab.Migrations.Sqlite / Lab.Migrations.Postgres
```

- **Lab.Domain** - сутності й правила предметної області. Жодних залежностей: ні EF Core,
  ні ASP.NET. Це перевіряється тестом `DependencyTests`.
- **Lab.Contracts** - те, що бачить клієнт: DTO, моделі запитів, валідація. Залежить лише від
  домену (щоб брати константи на кшталт меж довжини назви). Зміна контракту - це подія для
  всієї команди, тому вона завжди супроводжується оновленням OpenAPI й позначкою в PR.
- **Lab.Application** - сервіси, абстракції, розрахункове ядро. Знає про `IAppDbContext`, а не
  про `LabDbContext`. Конкретна СУБД тут не згадується жодного разу.
- **Lab.Infrastructure** - `LabDbContext`, Fluent-конфігурації, вибір провайдера. **Єдине місце
  в solution, де трапляються `UseSqlite` і `UseNpgsql`.**
- **Lab.Api** і **Lab.Worker** - точки входу: HTTP та фонова обробка.
- **Проєкти міграцій** - по одному на СУБД; залежать від інфраструктури, їх не залежить ніщо,
  крім точок входу під час виконання.

## 2. Чому два проєкти міграцій

Міграція - це не «модель», а згенерований DDL під конкретну СУБД плюс `ModelSnapshot`. Знімок
моделі один на набір міграцій, тому два провайдери в одній assembly перебивали б один одного:
друга міграція «не бачить» змін першої, а `dotnet ef` починає плутати набори. Окремий проєкт
на кожну СУБД плюс власна `*DesignTimeDbContextFactory` роблять застосування «не того» набору
неможливим навіть випадково.

Практичний наслідок: **одна зміна моделі - дві команди `migrations add` і два `database update`.**

## 3. Перемикання СУБД конфігурацією

Провайдер вибирає `DatabaseOptions.FromConfiguration`:

1. змінна середовища `LAB_DB_PROVIDER` (вищий пріоритет),
2. ключ `Database:Provider` у `appsettings.json`,
3. за замовчуванням - SQLite.

Залежність «провайдер → assembly міграцій» задана в одному методі `GetMigrationsAssembly()`.
Тому один і той самий код запускається і на SQLite (клієнт, локальна розробка), і на PostgreSQL
(сервер), а перемикання не потребує ні перезбірки, ні змін у коді.

## 4. Що абстрагує EF Core, а що залежить від провайдера

**Абстрагує:** формування запиту LINQ, переклад у мову бази, матеріалізацію результатів,
відслідковування змін, генерацію `INSERT/UPDATE/DELETE`, межу транзакції (`SaveChanges`),
асинхронні операції.

**Залежить від провайдера:** міграції та знімок моделі, типи колонок (зокрема `DateTime`,
`decimal`, `enum`), трансляція окремих методів, регістрозалежність порівняння рядків, порядок
`NULL` у сортуванні, підтримка `DateTimeOffset` (SQLite її не має), поведінка при конкурентних
конфліктах.

Тому ключові запити перевіряються на **обох** СУБД, а не тільки на тій, яка стоїть у розробці.

## 5. Що свідомо не входить у скелет

| Що | Чия зона | Чому так |
|---|---|---|
| Автентифікація, ролі, політики, аудит | Z3 | Це експертна зона: рішення про модель доступу ухвалює її власник, а не скелет |
| Клієнт MAUI та офлайн-синхронізація | Z4 | Потребує встановленого workload MAUI; проєкт створює власник зони (див. `src/Lab.Client.Maui/README.md`) |
| Розрахункове ядро (математика) | Z1 | Наповнюється разом з інваріантами серій вимірювань |
| Контейнеризація API | Z2 | `docker compose` для бази вже є; образ API додається разом із CI-публікацією |

## 6. Тести: три рівні

1. **Швидкі** (`Lab.Domain.Tests`) - правила домену, без бази й без HTTP. Сюди йде вся математика:
   чисте обчислення тестується дешево й повністю.
2. **Середні** (`Lab.Application.Tests`) - сервіси на SQLite у пам'яті: перевіряють логіку разом
   з EF Core, але без зовнішніх залежностей.
3. **Повільні** (`Lab.Postgres.Tests`) - те саме на реальній PostgreSQL. Без `LAB_TEST_POSTGRES=1`
   позначаються пропущеними, у CI виконуються обов'язково.

Порогова вимога - покриття ≥ 80 % - перевіряється скриптом
`scripts/coverage-summary.py`, який повертає код 1, якщо ядро нижче порога.

## 7. Коди відповідей на доступ до чужих ресурсів: 403 чи 404

Рішення одне на всю систему, щоб клієнт поводився передбачувано:

| Ситуація | Код | Чому саме так |
|---|---|---|
| Читання ресурсу, якого немає **або** який належить іншому користувачу | **404** | не розкриваємо існування чужого ресурсу |
| Спроба **зміни** ресурсу, який існує, але прав на дію немає | **403** | ресурс відомий, бракує прав за роллю |
| Дія конфліктує зі станом ресурсу (підписана серія, дубль) | **409** | ресурс доступний, але стан не дозволяє |

Дублюється в `docs/acceptance-cases.md` (кейси 7 і 10) - там це частина контракту.
